## 문제 해결 기록

### [PROB-009] 입력한 시간이 되돌아가고, 낮잠이 길어져도 뒤 수유가 안 밀림 (2026-08-11)

**문제 (Problem)**: 루틴이 꼬였을 때 다시 맞추라고 만든 도구인데 정작 입력이 안 먹혔다. 네 가지가 겹쳐 있었다.
1. 수유2를 12:00으로 옮긴 뒤 낮잠1을 건드리면 수유2가 10:30으로 **되돌아갔다**.
2. 수유 시간을 옮기고 새로고침하면 **전부 원위치**로 돌아갔다.
3. 낮잠2를 14:00~16:00으로 늘려도 수유3이 14:00에 그대로 박혀 있어 **낮잠 중에 수유가 끼어** 있었다.
4. 그 낮잠2조차 구간 밖이라는 이유로 12:00으로 **되돌려졌다**.

**원인 (Cause)**: 계산 결과인 `baseRows`를 상태에 저장해 두고 여기저기서 조각조각 수정하는 구조였다.
수유는 `pinFeedRows()`가 항상 `첫수 + 수유텀 × N`으로 **다시 못박았기 때문에**, 중간 수유를 옮겨도 다음 편집이나
새로고침 때 덮어써졌다. "어떤 카드를 사용자가 직접 입력했는지"를 기억하는 곳이 아예 없었다.
낮잠 편집은 뒤 낮잠만 다시 깔고 수유는 손대지 않아, 낮잠이 길어져도 수유가 밀리지 않고 낮잠이 구간에 눌려 찌그러졌다.
`autoShift`("뒤 일정 자동 밀기")는 켜져 있어도 `pinFeedRows()`가 곧바로 되돌려 **사실상 죽은 설정**이었다.

**해결 방법 (Solution)**: 스케줄을 저장 대상에서 빼고 **순수 계산 함수 `layoutSchedule()`** 하나로 통합했다.
저장하는 건 기본 설정과 `pinnedStarts`/`pinnedDurations`(사용자가 직접 넣은 값)뿐이고, 카드 목록은 매번 다시 계산한다.
계산 순서대로 훑으면서 자동값 위에 입력값을 얹고, 그 값을 그 뒤 계산의 기준으로 삼는다.
수유2를 옮기면 수유3·4가 수유텀만큼 따라오고, 낮잠이 길어지면 그 뒤 수유도 밀린다.
어떤 카드도 앞 카드가 끝나기 전으로는 못 가므로 낮잠3에 오전 시각을 넣어도 수유2 앞으로 튀지 않는다.
저장하는 값이 곧 입력값이라 새로고침해도 그대로 남는다. `↺`는 그 카드의 입력값만 지워 자동 계산으로 되돌린다.

**검증**: 핀·설정을 무작위로 조합한 30만 케이스에서 NaN/음수/순서 역전/구간 이탈/비결정적 결과가 0건.
브라우저에서 수유 이동 → 낮잠 편집 → 새로고침, 낮잠 연장 시 뒤 수유 밀림, 낮잠3 오입력 방어를 모두 확인했다.

### [PROB-008] 낮잠 시간을 고치면 `NaN:NaN`이 뜨고 카드 순서가 뒤바뀜 (2026-08-11)

**문제 (Problem)**: 낮잠 시간을 수정하다 보면 낮잠2·낮잠3 카드가 `NaN:NaN - NaN:NaN`, `깨시 NaN시간 NaN분`, `-NaN분`으로 깨졌다. 다시 시간을 넣으면 이번엔 낮잠 카드가 목록 맨 위(첫기상보다 앞)로 올라가고 `-1288분` 같은 값이 붙었다. 낮잠이 다음 수유를 넘어가도 아무도 막지 않았다.

**원인 (Cause)**: 세 가지가 겹쳐 있었다.
1. `normalizeTimeInput`이 입력값을 `[기준-1일, 기준, 기준+1일]` 중 기준 시각에 가장 가까운 값으로 고르는데, 기준 시각이 한 번이라도 `NaN`이 되면 `NaN` 비교가 전부 `false`라 무조건 **첫 후보(= 하루 전)**를 골랐다. 그래서 14:15가 -585분(음수)으로 저장됐다. 자정 넘김 보정이 필요한 카드는 막수뿐인데 모든 카드에 걸려 있던 것도 문제였다.
2. 저장값 검사를 `typeof x === "number"`로만 해서 `NaN`이 그대로 통과했다(`typeof NaN === "number"`). 한번 들어온 `NaN`은 `updateRowStart`/`updateRowDuration`의 `delta` 계산과 낮잠 재배치를 타고 뒤 카드로 번졌고, `clearFutureActualLogs`의 `start > now` 비교도 `NaN`이면 `false`라 깨진 기록이 지워지지 않고 남았다.
3. 카드 목록을 **시작 시각으로 정렬**하고 있어서, 시각이 음수가 되거나 `NaN`이 되면 카드 자리가 통째로 뒤바뀌었다.

**해결 방법 (Solution)**:
- `enforceScheduleLayout()`을 만들어 일정이 바뀌는 모든 길목(기본 스케줄 생성, 낮잠 재배치, 수유 고정)에서 한 번씩 통과시킨다. 수유·막수는 앞 수유가 끝난 뒤로만 갈 수 있고, 낮잠은 앞뒤 수유 사이에만 놓이며, 자리가 모자라면 낮잠 길이를 줄여서라도 구간 안에 넣는다.
- 카드 배치를 시작 시각 정렬에서 **기준 순서 고정**으로 바꿨다. "다음 일정"처럼 시간이 기준인 값은 목록 순서 대신 실제 시각을 비교하도록 고쳤다.
- `normalizeTimeInput`은 음수 후보를 아예 만들지 않고, 자정 넘김 보정은 막수 카드에만 적용한다.
- 입구(저장값·입력칸)와 출구(화면 표시 함수) 양쪽에 유한수 검사를 넣어 `NaN`이 상태에 들어오지도, 화면에 나가지도 않게 했다.

**검증**: 시간 수정·낮잠 길이 변경·빠른 기록·설정 변경·경고 적용·새로고침을 무작위로 섞은 6.4만 개 시나리오를 돌려 `NaN`/음수/순서 역전/구간 이탈이 하나도 없음을 확인했다.

**이미 깨진 기기 복구**: 고치기 전 버전이 휴대폰에 저장해 둔 음수 시각(예: -585분)은 유한한 숫자라 검사를 통과해 그대로 남아 있었다. 스케줄만 구간 안으로 당겨지고 카드에 찍히는 실제 기록은 옛 값 그대로여서 새 버전에서도 `14:15`처럼 보였다. 하루 범위를 벗어난 기록은 불러올 때 버리고, 낮잠 기록은 구간 안으로 맞춰진 시각으로 다시 쓰도록 해서 앱을 열기만 하면 저절로 정상으로 돌아오게 했다.

### [PROB-007] 이메일 수집이 실패해도 화면엔 "등록됐어요"가 떴음 (2026-07-24)

**문제 (Problem)**: 이메일 팝업이 어떤 상황에서도 성공 문구를 띄웠다. 웹훅 주소가 빌드에 안 들어간 경우엔 개발자용 안내문("웹훅 주소를 넣으면...")이 성공 메시지 자리에 그대로 사용자에게 노출됐고, 그 상태에서는 이메일이 구글시트에 한 건도 안 쌓이는데 사용자도 운영자도 알아챌 방법이 없었다.

**원인 (Cause)**: 두 가지가 겹쳤다. ①`WAITLIST_WEBHOOK_URL`이 비어 있어도 `try` 블록을 그냥 통과해 성공 처리했다. ②구글 Apps Script 웹앱은 CORS 헤더를 안 주기 때문에 `mode: "no-cors"`로 보내야 하는데, 이 모드에서는 응답이 opaque라 성공/실패를 읽을 수 없다. 게다가 타임아웃이 없어 응답이 안 오면 버튼이 "저장 중..."에 계속 머물렀다.

**해결 방법 (Solution)**: 웹훅 주소가 없으면 성공이 아니라 **에러로 처리**하고 문의 메일 주소를 안내한다. 전송 전에 `navigator.onLine`을 확인하고, `AbortController`로 10초 타임아웃을 걸어 네트워크 문제는 `catch`로 잡히게 했다. 다만 `no-cors` 특성상 **서버가 500을 주는 경우까지는 여전히 구분할 수 없다** — 접수 건수는 구글시트에서 주기적으로 직접 확인해야 한다.

### [PROB-006] 빠른 기록으로 낮잠 종료 시 다음 낮잠 시간이 실제 종료를 반영하지 않음 (2026-07-16)

**문제 (Problem)**: 낮잠을 빠른 기록 버튼으로 시작/종료하면 실제 종료 시각을 입력했는데도 다음 낮잠 시간이 계산상 낮잠 길이를 기준으로 남을 수 있었다.

**원인 (Cause)**: 수동 시간 편집은 뒤 스케줄을 다시 계산했지만, 빠른 기록의 낮잠 종료 처리는 실제 기록만 저장하고 낮잠 스케줄 재계산 함수를 호출하지 않았다.

**해결 방법 (Solution)**: 빠른 기록으로 낮잠을 종료할 때도 실제 시작/종료 시각으로 낮잠 길이를 계산한 뒤, 같은 재계산 흐름을 적용해 뒤 낮잠 시간이 실제 종료 기준으로 갱신되도록 했다.

### [PROB-005] 다음 날에도 전날 루틴 수정값이 남음 (2026-07-15)

**문제 (Problem)**: 하루용 루틴 계산 도구인데, 전날 입력한 실제 기록과 시간 수정값이 다음 날에도 남을 수 있었다.

**원인 (Cause)**: 로컬 저장 데이터에 루틴 날짜를 구분하는 값이 없었다.

**해결 방법 (Solution)**: 저장 상태에 `routineDate`를 추가했다. 앱을 열었을 때 저장 날짜가 오늘과 다르면 기본 설정은 유지하고 스케줄과 실제 기록만 초기화하며, 앱을 켜둔 채 12시를 넘겨도 날짜 변경을 감지해 저장된 기준값으로 새 스케줄을 계산하도록 했다.

### [PROB-004] PWA 백그라운드 알림이 실기기에서 신뢰 불가 (2026-07-14)

**문제 (Problem)**: GitHub Pages에 배포된 토닥루틴도우미 PWA에서 앱 화면이 휴대폰에 떠 있지 않으면 일정 알림이 오지 않았다.

**원인 (Cause)**: 정적 PWA의 화면 타이머, Web Worker, Service Worker 타이머는 휴대폰 OS와 브라우저 백그라운드 정책에 의해 정지될 수 있다. 정해진 시각에 안정적으로 알림을 보내려면 네이티브 앱 로컬 알림 또는 서버 기반 Web Push가 필요하다.

**해결 방법 (Solution)**: 도우미 PWA에서 알림 권한 요청, 일정 알림 등록, 알림 테스트 UI와 관련 예약 코드를 제거했다. 알림은 토닥루틴 Flutter 본 앱 또는 서버 기반 Web Push 단계로 분리한다.

### [PROB-001] 화면을 띄워 둔 경우에만 일정 알림 수신 (2026-07-14)

**문제 (Problem)**: 앱 화면이 보이는 동안에는 일정 알림이 오지만, 홈 화면으로 내리거나 다른 앱을 보고 있으면 알림이 오지 않거나 크게 늦어졌다.

**원인 (Cause)**: 일정 예약이 브라우저 화면의 `window.setTimeout`에만 의존했다. 모바일 브라우저는 숨겨진 화면의 타이머를 제한하고, OS 절전 정책에 따라 앱 프로세스를 멈출 수 있다.

**해결 방법 (Solution)**: Web Worker와 Service Worker 기반 보조 예약을 시도했지만 실기기에서 신뢰성이 충분하지 않았다. 최종적으로 PROB-004에 따라 도우미 PWA의 알림 기능을 제거했다.

### [PROB-002] 알림 등록 후 일정 입력값이 바뀌는 문제 (2026-07-14)

**문제 (Problem)**: 첫기상, 첫수, 낮잠 길이 등을 나중에 수정할 수 있어 알림 등록 시점을 사용자가 판단하기 어려웠다.

**원인 (Cause)**: 수동 등록 버튼 문구 때문에 알림 시간이 최초 등록값에 고정되는 것처럼 보였다.

**해결 방법 (Solution)**: 이후 실기기 검증 결과에 따라 도우미 PWA의 알림 기능을 제거했다. 수동 등록 버튼과 관련 설정도 함께 삭제했다.

### [PROB-003] 알림 아이콘이 미리보기 배경을 포함함 (2026-07-14)

**문제 (Problem)**: 토닥루틴 알림 아이콘 시안이 어두운 미리보기 배경을 포함해 실제 앱 자산으로 바로 사용할 수 없었다.

**해결 방법 (Solution)**: 선택된 아기 얼굴, 머리 꼭대기 C자 컬, 궤도 실루엣은 유지하면서 흰색 단색 + 완전 투명 배경 PNG로 변환했다. 512px 마스터와 192px, 96px 파생 파일의 알파 채널과 RGB 값을 검증했다.
